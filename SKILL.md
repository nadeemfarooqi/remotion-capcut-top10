# Remotion → CapCut Top-N countdown pipeline

Builds a "Top N [category]" countdown video as a **real CapCut project draft**, generated
entirely from code (no manual timeline editing), with the flashy animated parts rendered
separately in **Remotion** and composited into the CapCut draft as video clips. Reference
implementation: `/Users/nad/Desktop/camping-gadgets` (the CapCut-draft builder, pure Python) +
`/Users/nad/Desktop/gadget-videos` (the sibling Remotion project the overlays are rendered
from). Treat these as *a* working example, not the only possible layout — when bootstrapping an
unrelated new Top-N project, reuse the patterns below, not necessarily the exact file names.

**Why CapCut-plus-Remotion instead of a pure Remotion render**: a pure-Remotion video's overlays
are positioned by blind coordinates baked into React code, which drifts/misaligns in ways that
are hard to debug and impossible for a non-engineer to nudge by hand. Assembling in CapCut
(via `pycapcut`) instead gives provably-correct, hand-adjustable positioning — the user can open
the real CapCut UI and nudge anything. Remotion still does the actual animation (CapCut's own
motion tools are far more limited); it just renders to a clip that CapCut treats as regular
footage. See "Core technique" below for exactly how that handoff works.

## Architecture

Two sibling folders, one pipeline:

- **The CapCut-draft builder** (pure Python + `pycapcut`). Writes directly into
  `~/Movies/CapCut/User Data/Projects/com.lveditor.draft/<DraftName>/` and registers itself in
  that folder's `root_meta_info.json` (`all_draft_store` array), so the draft shows up in
  CapCut's own project list with no import step. Not usually git-tracked (media-heavy).
  ```
  data/gadgets.json          the N items: name/category/specs/price/rating/bestFor/brand,
                              plus a curated spec_animations array and optional illustration
                              field (see Layers 2 & 3)
  data/narration.json        spoken script per item + intro/outro
  data/timing.generated.json AUTO-GENERATED by the voiceover script from actual TTS speech
                              length (frames @ 30fps per item) — never hand-edit
  media/<rank>/film.mp4      sourced b-roll per item
  media/<rank>/hero.jpg      a photo of the item (used by the count card + Layer-3 illustrations)
  media/<rank>/meta.json     {video, clip_starts, hero_image, credit} — clip_starts are
                              hand-picked second-offsets into the source video (scan an ffmpeg
                              contact sheet) so cuts land on clean footage, not the source's own
                              baked-in caption/logo cards
  media/<rank>/overlays/     Remotion-rendered clips this builder consumes: countcard.mp4
                              (opaque), spec1.mov/spec2.mov (alpha), illustration.mov (alpha) —
                              generated by the Remotion project's render script, never hand-edited
  scripts/build_capcut_draft.py   the single source of truth. Reads everything above, uses
                              pycapcut to construct the draft JSON, writes + registers it. Fully
                              regenerates every run — safe to re-run any time data/media changes
  scripts/lib/layout.py      the overlay coordinate system (see "Positioning" below)
  scripts/voiceover.py + scripts/lib/timing.py   TTS narration + word-alignment timing
  .venv                      Python venv with pycapcut installed
  ```
- **The Remotion project** (TypeScript/React). Renders every animated overlay to a video file
  the builder above picks up. Also owns `public/<something>/<rank>.jpg` copies of the hero
  images, since Remotion's `staticFile()` needs assets under `public/` (a bare absolute path or
  `file://` URI is not reliable in headless render).
  ```
  src/components/CountCard.tsx           Layer 1 — full-screen rank reveal
  src/components/RankCounterBadge.tsx    the reusable circular rank-number badge inside it
  src/components/SpecCounterOverlay.tsx  Layer 2 — small spec/stat badge
  src/components/HeroIcons.tsx           Layer 2b — per-category animated icon library
  src/components/<Name>Illustration.tsx  Layer 3 — one file per bespoke illustration
  src/Root.tsx                           registers every overlay Composition; comment each one
                                          with which build_capcut_draft.py constant its
                                          durationInFrames must match
  scripts/render-overlays.mjs            batch-renders everything above, writes into the
                                          CapCut-side project's media/<rank>/overlays/
  ```

## Core technique: Remotion renders, CapCut assembles

Two compositing modes — pick based on whether the piece needs to see through to footage:

**1. Alpha overlay** (badges, illustrations — anything meant to sit on top of footage). Render
on a transparent canvas with a real alpha channel, then add it as a plain video segment on a
CapCut track *above* the footage track:
```python
script.add_track(pycapcut.TrackType.video, "specfx", relative_index=1)  # higher = more foreground
script.add_segment(pycapcut.VideoSegment(material, timerange), "specfx")
```
No chroma key needed, and no CapCut-side transform math either — draw the content at its target
pixel coordinates *inside* the full-canvas Remotion comp, then place the whole frame at CapCut
transform (0,0) scale 1. This is what sidesteps the blind-coordinate drift that pure-Remotion
overlays suffer from.

Render command — **all four flags are required together**:
```bash
npx remotion render <CompositionId> out.mov \
  --codec=prores --prores-profile=4444 \
  --pixel-format=yuva444p10le --image-format=png \
  --props='{...}'
```
`--codec=prores --prores-profile=4444` alone silently renders **opaque** (composited onto
white). `--pixel-format=yuva444p10le` is the alpha-carrying pixel format; `--image-format=png`
is required so intermediate frames are captured with alpha before encoding (omit it and Remotion
errors: "Pixel format was set to yuva444p10le but the image format is not PNG"). Always verify
with `ffprobe -show_entries stream=pix_fmt` — it must read `yuva...`, not `yuv...`. Don't trust
how a transparent PNG/video looks in a plain viewer (it renders as flat white either way,
transparent or not) — prove real transparency by compositing a test frame over a solid color
with ffmpeg first.

**2. Opaque replacement** (the count card — anything meant to fully *take over* the screen for
its own window). Render as a normal opaque clip (`--codec=h264`, no alpha flags — simpler,
faster) and place it directly on the **base** video track, sequenced ahead of or between footage
segments, instead of overlaying it. Never alpha-overlay something meant to be a full-screen
beat — there's nothing to show through anyway, and it's needless extra render cost.

**Recurring gotcha**: Remotion's `--props` shallow-*merges* over the Composition's `defaultProps`
in `Root.tsx`, it does not replace it. If `defaultProps` sets `value: 1800`, a render that omits
`value` (e.g. a caption-only variant of the same component) will still show that leaked `1800`.
Keep `defaultProps` free of any field that's meant to be conditional/optional for a composition.

Batch-render with a plain Node `.mjs` script using `execFileSync` per `npx remotion render` call,
one call per variant with different `--props` JSON — no need for a Composition per variant. Keep
each comp's internal animation timing as *fractions* of `durationInFrames`, not hardcoded frame
numbers, so the same comp works at whatever duration gets passed to it.

## The three-layer overlay system

The creative and structural heart of this pipeline. Every project built with this skill should
have all three; Layer 3 is the one meant to keep growing project over project.

### Layer 1 — Count card (full-screen, opaque, one per item)

The classic countdown-video convention: a big rank-number reveal that plays as its **own beat**
before that item's footage — not an overlay sitting on top of footage. Insert it on the base
video track ahead of the item's b-roll cuts, eating into that item's own timeline slot (don't
extend the slot — let the b-roll and any per-item text fill only what's left, so narration
timing for the item is untouched).

Reference implementation (`CountCard.tsx`, ~2.2s / 66 frames @ 30fps, tune to taste): a
blurred/dimmed backdrop of the item's own photo, `RankCounterBadge.tsx` at large size landing
center-stage (a solid accent-colored circle with the digit inside, revealed by a **white ring
sweeping around it via `stroke-dashoffset`** — not a fade, that radial-sweep reveal is the
specific visual the "count card" ask is usually pointing at), a few small floating
accent-colored particles for atmosphere, category + item name sliding up below.

**Hard-won lesson — "counter"/"count card" means THIS, not a stat counter.** It took three
rejected attempts in the reference project to land here, so don't repeat the path:
1. A small ghost-number + sliding-text overlay ON TOP of footage → rejected as "boring."
2. A bigger side-anchored card overlaid on footage with a *stat* number + item photo + name →
   still wrong. The user's reference to a circular radial-sweep-reveal badge was about the
   **rank** number's style, not a spec/stat value — don't conflate "an animated number" for a
   rank position with "an animated number" for a stat like "1,800W".
3. Combined the circle-reveal badge with a photo+name card, still overlaid on footage → still
   wrong. The missing piece was **full screen** — an actual timeline segment that *replaces*
   what's on screen, not something composited on top of it.

General rule: in a Top-N countdown, the rank-number reveal is a full-screen interstitial beat,
separate from any per-item stat callouts over the b-roll. If a request is ambiguous between "big
number = rank" and "big number = a stat", a countdown format almost always means the rank —
ask rather than guess twice.

### Layer 2 — Small spec/stat badges (alpha overlay, small, 1-2 per item, THESE STAY SMALL)

A corner-ish badge (~340px content width) composited over the b-roll mid-item, at a fixed
fraction-of-scene window (reference: two windows around 38%-60% and 64%-86% of the item's own
duration). Reference shell (`SpecCounterOverlay.tsx`): dark translucent rounded card, accent
border + glow, a small (~64px) icon box on the left showing a per-category animated icon (Layer
2b), a mono-font label above, and either a digit count-up (`value`/`unit`/optional `decimals` —
decimals matter for sub-1 values like "0.1 micron" so the count-up doesn't round to 0) or a short
caption phrase instead of a number (for non-numeric callouts, e.g. "2-way, works anywhere") —
same card shell either way, so a scene never visually jumps depending on which kind a slot got.

Curate which spec gets an animated badge **by hand**, per item, from the actual spec text — do
not auto-parse free-text specs, since many are ranges or classification codes ("-7°F to 50°F",
"IP67") that shouldn't be flattened into a fake counter. Slots that don't parse into a clean
number+unit or good visual fall back to plain static text in the exact same on-screen position.

**Hard rule**: a user explicitly rejected an attempt to enlarge these badges ("these remain as
it is") when what they actually wanted was *more overlays elsewhere* (Layer 3), not bigger
versions of Layer 2. Don't resize or restyle Layer 2 without being explicitly asked. When a user
says the overlays should be "bigger" or "more" after Layer 2 already exists, default to reading
that as "add Layer 3 illustrations" — confirm before touching Layer 2's size/position.

### Layer 2b — Per-category animated icon library (`HeroIcons.tsx`)

One small animated SVG icon per category/visual-key (reference has ~12: charging bolt, clearing
smoke, thermometer fill, satellite ping, waveform/equalizer, flickering flame, tent pop-up,
light-beam sweep, depth gauge with waterline, water-droplet flow, camera-lens iris, wifi signal
arcs). Each is driven by the *same* frame clock as the badge/card around it, so icon motion and
count-up/caption timing always stay in sync — roughly 30-60 lines of inline SVG with simple
sine/interpolate-driven animation, never static.

**Core principle** (a real user correction, state it plainly): don't default to one generic
reused icon/animation for every item just because it's less work. Design a distinct,
thematically-matched icon per category — a satellite ping for a satellite communicator, a
rising thermometer for a fridge, a flame for a stove, a tent popping up for a tent — the way a
human motion designer would treat "what's the one bespoke thing about *this* item" as a real
per-item question. Reusing one generic counter+icon everywhere reads as lazy and gets called out
directly ("why your shy to use these components to actually stand out").

### Layer 3 — Bigger, bespoke feature illustrations (alpha overlay, medium size, ADDITIVE)

Not a resize of Layer 2, not a replacement for anything — a genuinely separate, bigger (but not
full-screen — Layer 1 owns full-screen) illustration for **one specific feature of one specific
item**, composited in whatever time gap that item's scene has free. Reference: a dedicated
window fraction (e.g. 10%-34% of the scene) sized to avoid the count card and the Layer-2 badge
windows, gated by a data field per item (e.g. `"illustration": {"component": "<Name>"}`) checked
against a corresponding `media/<rank>/overlays/illustration.mov`.

**This is the section meant to keep growing.** Each entry should be a real, hand-designed idea,
not a formula. Reference examples built so far:
- **Two-way satellite messaging** (`TwoWayCommsIllustration.tsx`): a handheld device on the
  ground sends a message packet — with a comet-trail, not just a dot — arcing up to a satellite
  (gradient-shaded body, ribbed solar panels, blinking antenna, gentle orbital sway, an
  *expanding ping-ring* on arrival, not just a steady glow) over a quiet starfield, then replies
  back down. Runs twice so both directions read clearly.
- **Smart-fan smoke reduction** (`SmokeReductionIllustration.tsx`): not an icon+number at all —
  a small before/after story. A smoky, messy fire; the fan visibly spins up at its base; over a
  few seconds the smoke thins out while the flame itself grows a physically-plausible clean-blue
  combustion wedge and starts throwing embers, with the percentage counting up *in sync* with the
  visual transformation instead of sitting static next to a decorative icon.

**Creative direction**: favor illustrations that tell a small transformation/story (before →
after, problem → solution) over ones that just decorate a number, whenever the underlying
feature has an inherent before/after (a reduction %, a speed claim, a capability contrast). This
reads as far more creative and modern than a bigger version of the Layer-2 pattern, and it's
what a "make it more thoughtful/creative" request is usually actually asking for.

**Required process — one illustration at a time, confirm, then the next.** This isn't a
suggestion; skipping steps here is exactly what caused repeated do-overs in the reference
project:
1. Design the concept — what real-world thing is this item's feature, and what's the simplest
   honest way to *show* it working (a device sending/receiving, a substance getting cleaner, a
   material changing state)?
2. Render a **still** frame first. Cheap, and it catches structural bugs immediately — e.g. a
   hand-authored flame SVG path that reads as a leaf or teardrop instead of fire needs fixing
   before anyone sees motion.
3. Render a short **preview video**, then composite it over a plain dark color with ffmpeg for
   review (white text/elements are invisible against a transparent file's white-in-viewer
   rendering, which reads as a false "it's missing" bug otherwise — always verify true
   transparency by test-compositing over a solid color).
4. **Send it to the user and wait for approval** before wiring it into the real draft or
   starting the next illustration. Don't batch-build multiple new Layer-3 pieces ahead of
   approval.
5. Only after approval: render to alpha, add the data marker, rebuild the CapCut draft, and
   **verify in the actual installed CapCut app** — scrub the real timeline, screenshot/zoom the
   real preview panel, confirm it composites over real footage. Don't call it done from
   inspecting the rendered clip in isolation.

## Positioning (`layout.py` / the coordinate system)

CapCut's `clip.transform.{x,y}` is center-anchored, normalized to canvas half-width/half-height,
and Y is flipped (positive y = up). Text is *always* center-anchored regardless of the `align`
field (align only affects multi-line justification within the block, not the anchor point).

Design principle: put anything that can overflow dead-center horizontally (`x = canvas_w / 2`),
so it structurally cannot clip left or right no matter the string length — no width estimate
needed. Only bother estimating rendered width for genuinely corner-anchored elements (e.g. a
bottom-left credit line), and clamp that estimate so it can never push off-canvas even if wrong.
This is *the* fix for "overlays not aligned" complaints, which is usually the whole reason this
CapCut-plus-Remotion approach got picked over a pure-Remotion render in the first place.

## Before touching pycapcut internals or debugging a CapCut-side issue

Read `references/capcut-format-notes.md` — verified-against-a-real-install notes on: where the
draft files actually live and how `root_meta_info.json` registration works (including that
`pycapcut`'s own draft-remove call does *not* clean that file up), sandboxing and why every
media asset must be copied into the draft's own folder, which pycapcut features are
confirmed-working vs. confirmed-broken, and the verification quirks (stale window state, display
sleep, preview-not-refreshing) that cause false readings if you don't know about them.

## Timeline math

Every timestamp/duration in the builder is an **integer microsecond**, computed from a single
source of truth per boundary — never `float seconds → string → reparsed`. Two independently
rounded float→string→microsecond conversions of "the same" boundary can differ by 1
microsecond, which CapCut's segment-overlap check will (correctly, if confusingly) reject as a
genuine overlap.
